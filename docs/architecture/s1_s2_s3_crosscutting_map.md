# S1 / S2 / S3 横向架构图

S1、S2、S3 是横向治理能力，不是可选的普通业务页面。它们贯穿 L0–L7 的关键动作，用于保证运行范围明确、候选经过治理、来源能够追溯。

```text
                     L0 → L1 → L2 → L3 → L4 → L5 → L6 → L7
S1 运行上下文          ─────────────────────────────────────────→
S2 治理闸门                 ──重点作用于 L1 到 L2，并约束后续动作──→
S3 审计追踪            ─────────────────────────────────────────→
```

## S1：运行上下文

S1 负责为当前请求提供受控运行范围。

主要内容：

- 当前用户；
- 所属组织；
- 当前角色；
- 项目范围；
- 允许动作；
- 上下文来源和标识；
- 必要的设备、位置或会话信息。

主要作用：

1. 在业务路由执行前确认当前请求属于谁、在哪个组织和项目中发生。
2. 防止不同项目、组织和用户的消息、候选或待确认状态混用。
3. 为权限判断、审计记录和业务查询提供上下文。

边界：

- 前端可展示和选择上下文，但不能自行决定最终权限。
- 本地项目上下文不等于已经创建正式项目资产。
- 运行上下文变化后，前端应清理不再适用的临时状态。
- 后端业务路由必须复核 S1，而不是信任前端传入值。

## S2：治理闸门

S2 位于候选与正式事实之间，是事实入链的必要条件。

主要校验：

- 候选字段是否完整；
- 类型是否明确；
- 来源是否受控；
- 是否存在冲突、风险或缺失；
- 当前状态是否允许进入下一步；
- 是否需要人工确认、补充或阻断。

典型处理方向：

```text
need_confirm      → 进入人工确认
ask_more          → 补充关键信息
blocked           → 阻断并提示原因
ready_to_chain    → 仍由后端按既定确认和入链规则处理
```

边界：

- AI 不拥有 S2 放行权。
- H5 和 PC 不得根据页面按钮直接认定治理通过。
- S2 结果必须由后端返回并与候选、输入会话关联。
- 人工确认不能替代缺失的治理记录。
- L2 写入必须再次复核治理状态和确认记录。

## S3：审计追踪

S3 负责记录关键动作的来源、主体、对象和状态变化。

应覆盖：

- 谁在什么上下文中发起动作；
- 动作针对哪个输入、候选、治理记录或事实；
- 动作前后状态；
- 发生时间和来源；
- 分析、建议、执行和反馈之间的关联；
- 异常、失败和人工处理记录。

边界：

- S3 记录行为，不替代业务事实。
- 审计记录不得成为绕过 L2 的另一套事实真源。
- 审计数据需要可追溯，但不能包含不必要的明文密钥或敏感环境信息。
- 失败动作同样应保留必要追踪信息。

## 三者协同

```text
S1 回答：当前请求属于谁、在哪个范围、允许做什么？
S2 回答：当前候选是否满足治理要求、下一步是什么？
S3 回答：谁在何时对什么做了什么，状态如何变化？
```

三者共同约束纵向链路：

1. 没有有效 S1，不进入受保护业务路由。
2. 没有有效 S2 和人工确认，不创建 L2 正式事实。
3. 关键动作没有 S3 追踪，不应视为完整闭环。

## 开发要求

- S1、S2、S3 的字段、状态和动作必须与 contracts 保持一致。
- 前端只展示和发起动作，不复制后端治理规则。
- 新增 L4–L7 能力时必须明确其 S1 权限范围、S2 治理边界和 S3 审计点。
- 模块存在、接口返回或页面展示均不能单独作为横向治理完成的证据。
