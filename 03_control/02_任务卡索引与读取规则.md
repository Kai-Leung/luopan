# 02_任务卡索引与读取规则

文件名：02_任务卡索引与读取规则.md  
文件类型：任务卡读取控制文件  
目录架构版本：ARCH_DIR_v0.1.0  
用途：规定 Codex / 本地开发执行任务卡时，如何读取任务卡、映射总表、开发依据和目标目录。  

---

## 1. 文件定位

本文件只解决一个问题：

> Codex 执行某一张任务卡时，应该读取哪些资料、修改哪些目录、禁止修改哪些目录。

本文件不负责：

- 编写代码；
- 直接替代任务卡；
- 直接替代开发依据；
- 判断阶段最终验收通过；
- 指挥执行器自由修复问题。

---

## 2. 总读取原则

Codex 不得全量自由读取全部开发依据后自行开发系统。

每次只能按当前任务卡读取必要资料。

标准读取顺序为：

```text
当前任务卡
↓
本文件中的任务卡索引
↓
01_开发依据与目录映射总表.md
↓
任务卡指定的开发依据原文
↓
任务卡指定的允许修改目录
↓
技术选型与实现约束文件
↓
按任务卡要求生成或修改代码
↓
按任务卡要求回传结果
```

---

## 3. 每张任务卡必须包含的字段

| 字段 | 说明 |
|---|---|
| 任务编号 | 唯一编号，例如 `TASK-L0L1-001` |
| 任务名称 | 简明说明本任务要完成什么 |
| 任务目标 | 本任务要形成的可验收结果 |
| 依据来源 | 本任务必须读取的开发依据文件或章节 |
| 目录落位 | 本任务允许修改的目录 |
| 禁止目录 | 本任务禁止修改的目录 |
| 技术约束 | 必须遵守的技术选型和实现边界 |
| 验收重点 | 本任务完成后必须验证什么 |
| 回传要求 | 完成后必须返回哪些材料 |

---

## 4. 任务卡读取规则

### 4.1 先读任务卡

Codex 必须先读取当前任务卡，不得先自由分析整个仓库。

### 4.2 再查本文件索引

根据任务编号，在本文件第 8 节查找：

- 任务归口；
- 必读依据；
- 允许修改目录；
- 禁止修改目录；
- 验收重点。

### 4.3 再查映射总表

读取：

```text
03_control/01_开发依据与目录映射总表.md
```

确认：

- 当前目录是否承接该开发依据；
- 当前能力是否属于当前目录职责；
- 是否存在禁止误用。

### 4.4 再读开发依据原文

只读取任务卡指定的开发依据原文。  
不得因为任务相关，就全量读取全部开发依据并自由扩展。

### 4.5 最后读取允许修改目录

只读取和修改任务卡允许的目录。  
如果发现需要改其他目录，必须停止并回传“需要新增任务卡或用户裁决”。

---

## 5. 允许修改规则

Codex 只能修改任务卡明确列出的目录或文件。

如果任务卡写明：

```text
允许修改：
- services/api/app/modules/l0_input/
- services/api/app/modules/l1_candidate/
- packages/contracts/schemas/l0_input.schema.json
- packages/contracts/schemas/l1_candidate.schema.json
```

则不得修改：

```text
services/api/app/modules/l2_fact/
apps/pc/
apps/mobile-shell/
.env
data/
storage/
```

除非任务卡明确允许。

---

## 6. 禁止动作

任何任务卡默认禁止以下动作：

```text
1. 修改 .env 或写入密钥
2. 操作正式数据库
3. 清空 Raw Store
4. 清空 storage
5. 删除审计、trace、日志
6. 绕过 S2 直接写 L2
7. 让前端、AI、外部协同、上传资料直接生成正式事实
8. 将 L3 查询、L4 分析、L5 建议、L6 执行、L7 反馈反写为正式事实
9. 自行新增未在开发依据或任务卡中归口的模块
10. 自行引入新框架、新语言、新运行时
11. 未授权执行 git add / commit / push
12. 将页面可点、HTTP 200、构建通过、无报错判定为验收通过
```

## 7. 任务状态口径

| 状态 | 含义 |
|---|---|
| `待执行` | 任务卡已生成，尚未执行 |
| `执行中` | Codex 或本地开发正在执行 |
| `需补充依据` | 当前任务缺少必要开发依据或目录映射 |
| `需拆分` | 当前任务过大，需要拆成更小任务 |
| `需用户裁决` | 出现越界、冲突或高风险操作，需要用户判断 |
| `已回传` | 已完成代码修改并提交回传材料 |
| `待验收` | 已回传，等待独立验收 |
| `已通过` | 经独立验收通过 |
| `退回修补` | 验收未通过，需要生成修补任务 |

## 9. 任务卡执行边界

### 9.1 单任务只做一个闭环

每张任务卡应覆盖一个可验收闭环，不做全系统开发。

例如：

```text
TASK-L0L1-001 = 输入 + 候选
TASK-S2-001 = 校验 + 待补 + 确认 + 阻断
TASK-L2L3-001 = 入链 + 查询
```

### 9.2 发现缺口时停止

如果 Codex 发现以下情况，必须停止并回传：

```text
1. 开发依据缺失
2. 映射总表未覆盖
3. 需要修改任务卡外目录
4. 需要新增模块
5. 需要改 .env
6. 需要操作 data/storage/正式数据库
7. 技术选型冲突
8. 当前任务过大
```

### 9.3 不允许自行补规则

Codex 不得因为“看起来合理”自行新增：

```text
worker
webhook
flow-engine
auth-center
file-center
message-center
generic-crm
generic-erp
admin-platform
```

除非任务卡明确要求，且开发依据已有支撑。

---

## 10. 回传要求

每张任务完成后，必须回传：

```text
任务编号
执行状态
实际读取的依据
实际修改文件
新增文件
删除文件
涉及 contracts
涉及数据模型
执行的测试命令
测试结果
未执行测试及原因
是否修改 .env
是否修改 data/storage
是否执行 git add/commit/push
风险和阻断项
```

未回传上述内容，不得判定任务完成。

---

## 11. 结论

本文件是任务卡读取和索引规则文件。

它的作用是：

```text
任务卡
→ 必读依据
→ 允许目录
→ 禁止目录
→ 验收重点
→ 回传要求
```

后续所有代码开发必须通过任务卡执行，不得只凭目录总表或开发依据自由开发。
