# 罗盘技术选型方案

## 一、文件定位

本文用于上传到“罗盘系统｜拆解与实现工作台”的知识库，作为开发实现设计、窗口1阶段任务拆解、窗口2代码包生成、窗口3执行器任务卡或命令卡生成、执行器回传审查和窗口4阶段验收参考的技术选型依据。

本文不替代《COMMON_罗盘系统正式开发依据包.zip》。正式开发依据包决定系统边界、业务规则、数据真源、候选与正式边界、接口边界、页面承接和验收规则；本文只决定开发实现层面的技术路线。

本文采用“全阶段统一技术路线 + 当前启用范围 + 后续启用条件”的方式，不采用临时性、一次性、不可迁移的技术方案。

本文与其他知识库文件的锚定不以文件名版本号作为主依据，按 `COMMON_` / `RUN_` / `WINDOW_` 前缀加文件名主体识别；版本号只作为文件内部元信息和新旧优先参考。

## 二、技术选型总原则

1. 技术路线按罗盘系统最终形态一次性确定。
2. 当前本地 H5 + 本地服务器只作为开发验证、早期试用和问题发现方式。
3. 最终移动端形态为 Android / iOS 双端可安装 App，不是简单 H5 页面。
4. 最终运行形态支持本地专用服务器或云端服务器部署。
5. 代码结构从第一阶段开始必须支持后续迁移、扩展和部署。
6. 后端统一承接正式事实、权限、状态、追溯、Audit / Trace 和 L2 入链。
7. 前端、H5、App 只负责输入、展示、提醒、查询、确认请求和用户体验，不反向定义正式事实。
8. GPT 负责生成代码包；OneClaw / OpenClaw 只作为受控执行器落位、执行、测试、构建、预览和回传。

## 三、最终系统形态

罗盘系统最终形态为：

- Android / iOS 双端可安装 App；
- H5 移动页面体系；
- PC Web 管理工作台；
- 后端 API 服务；
- 数据库服务；
- 文件存储服务；
- 异步任务服务；
- AI 辅助服务；
- 权限、审计与追溯服务；
- 可从本地部署验证迁移到专用服务器或云端服务器运行。

当前 H5 页面是前期验证形态、移动端页面体系基础和 App 壳承接基础，不是最终形态边界。

## 四、统一技术路线总表

| 领域 | 统一选型 | 说明 |

## 五、前端与 App 选型

### 5.1 前端基础

前端统一采用：

- React；
- TypeScript；
- Vite。

该技术体系用于：

- H5 移动端页面；
- PC Web 管理工作台；
- 外部协同页面；
- 客户 / 甲方脱敏展示页面；
- 后续 App 内页面体系。

### 5.2 移动 App

移动端最终采用：

- Capacitor；
- Android App；
- iOS App。

路线为：

H5 页面体系 → Capacitor 封装 → Android / iOS 双端可安装 App → 按需接入相机、文件、语音、通知、离线草稿等原生能力。

### 5.3 前端职责

前端负责：

- 输入入口；
- 上传入口；
- 候选展示；
- 待补提示展示；
- 确认请求入口；
- 查询条件选择；
- 事实详情展示；
- 追溯入口；
- 状态提示；
- 页面体验；
- Mock 演示。

前端不得负责：

- 正式事实生成；
- L2 入链；
- 权限裁决；
- 状态真源；
- 风险裁决；
- 证据成立判断；
- AI 裁决；
- 外部反馈确认；
- 正式数据写入。

## 六、后端选型

后端统一采用：

- Python；
- FastAPI；
- SQLAlchemy；
- Repository 层；
- Service 层。

后端必须采用以下分层：

API Layer → Service Layer → Repository Layer → SQLAlchemy → Database

禁止业务代码直接散落操作数据库。

后端核心服务应按以下方向组织：

- Raw Input Service；
- Candidate Service；
- Confirmation Service；
- L2 / Fact Chain Service；
- Query Service；
- Trace Service；
- Access Control Service；
- Storage Service；
- Task Service；
- AI Service；
- Audit / Trace Service。

第一阶段不要求所有服务做满，但代码结构必须能容纳这些服务。

## 七、数据库与迁移路线

数据库路线为：

- SQLite：阶段验证数据库；
- PostgreSQL：正式运行目标数据库。

SQLite 用于：

- 本地开发；
- 本地部署验证；
- 早期单人试用；
- 最小闭环验证；
- 低并发测试。

PostgreSQL 用于：

- 专用服务器正式部署；
- 云端服务器正式部署；
- 多用户使用；
- 外部协同；
- 长期数据沉淀；
- 权限与审计增强；
- 后续性能扩展。

从第一阶段开始必须避免：

- 业务代码写死 SQLite；
- 数据库路径写死；
- 直接使用 SQLite 专属 SQL；
- 业务逻辑依赖本地文件绝对路径；
- 前端 API 写死 localhost。

必须采用：

- SQLAlchemy；
- Repository 层；
- Service 层；
- 数据库 URL 配置化；
- 环境配置隔离。

Alembic 在数据模型稳定后启用，不作为第一阶段开发阻断项。

## 八、文件存储路线

文件存储统一采用：

Storage Service 抽象 → 本地文件存储先行 → 后续兼容服务器文件系统或对象存储。

本地开发和验证可使用：

- storage/uploads_dev/
- storage/uploads_deploy/

业务系统不得直接依赖本地绝对路径。

数据库中应保存：

- 文件 ID；
- 相对路径；
- 资料类型；
- 来源；
- 上传主体；
- 关联对象；
- 追溯关系；
- 访问权限。

后续可迁移到：

- 服务器文件系统；
- MinIO；
- S3-compatible storage；
- 云厂商对象存储。

## 九、异步任务路线

异步任务统一采用：

Task Service 抽象 → 数据库任务表 + Worker 先行 → 后续按压力升级 Redis / Celery。

可用于：

- 文件识别；
- AI 调用；
- 模板生成；
- 资料处理；
- 导出任务；
- 回执处理；
- 批量处理。

第一阶段可以轻量预留，不强制复杂 Worker。任务结构应预留：

- 任务状态；
- 任务类型；
- 任务输入；
- 任务输出；
- 失败原因；
- 重试次数；
- 执行时间。

当 AI、文件识别、导出、模板、外部回执等任务明显增多后，再引入 Redis / Celery。

## 十、AI 与模型接口路线

AI 统一采用：

- 云端大模型 API；
- AI Service 封装；
- 模型配置化；
- 后续可扩展本地模型，但当前不启用。

AI 允许用于：

- 语音 / 口语输入转译；
- 候选内容预处理；
- 候选归整；
- 疑似缺口提示；
- 复杂文本辅助分析；
- 规则差异记录；
- 受控建议。

AI 不得：

- 裁决事实；
- 裁决权限；
- 裁决风险；
- 放行状态；
- 直接写正式事实；
- 替代 L2 入链；
- 替代人工确认；
- 替代正式规则发布。

AI 调用应记录：

- 调用场景；
- 输入；
- 输出；
- 模型；
- 成本；
- 失败原因；
- 人工是否采纳；
- 与直接校验结果的差异。

## 十一、缓存路线

缓存统一采用：

Cache Service 抽象 → 当前不强制 Redis → 后续按压力启用 Redis。

第一阶段可使用：

- 后端上下文缓存；
- 查询结果短缓存；
- 进程内缓存；
- 数据库索引优化；
- 前端局部状态缓存。

出现查询压力、多用户会话、AI 上下文缓存、热点数据访问或任务队列升级需求后，再启用 Redis。

## 十二、权限、审计与追溯路线

权限统一由后端 Access Control Service 控制。

后端控制：

- 用户身份；
- 组织范围；
- 项目范围；
- 主体范围；
- 操作权限；
- 查询权限；
- 外部展示权限；
- 脱敏规则。

前端隐藏按钮不能替代后端权限判断。

审计与追溯统一采用 Audit / Trace Service。

第一阶段至少记录：

- 操作主体；
- 操作时间；
- 操作动作；
- 原始输入；
- 候选版本；
- 确认请求；
- L2 入链结果；
- 查询范围；
- 失败原因；
- 资料关系。

后端控制正式事实、状态、权限、追溯和 L2 入链。前端、H5、App 只负责输入、展示、提醒、查询和确认请求。

## 十三、接口与联调路线

接口风格采用：

- REST API 先行；
- OpenAPI 自动文档；
- 后续按需预留 SSE。

第一阶段接口类别只围绕：

- 输入提交；
- 候选查询；
- 确认请求；
- L2 入链结果查看；
- 查询结果；
- 追溯查看；
- 失败 / 待补提示。

后续可在 AI 处理、资料识别、上传处理、长任务状态等场景引入 SSE。

暂不引入 WebSocket，除非后续出现强实时协同需求。

## 十四、部署路线

部署路线为：

本地开发 → 本地部署验证 → 局域网 / 手机访问验证 → 专用服务器或云端测试部署 → 专用服务器或云端正式运行 → Android / iOS App 连接正式后端 API。

本地电脑上应区分：

- 开发环境；
- 部署验证环境。

开发环境用于：

- 写代码；
- 调试；
- 跑测试；
- 接 GPT 代码包；
- OneClaw 落位修改；
- 允许失败；
- 允许重置数据。

部署验证环境用于：

- 模拟正式运行；
- 手机访问验证；
- H5 验证；
- 小范围试用；
- 保留相对稳定数据。

即使在同一台电脑，也必须分开：

- 目录；
- 端口；
- 数据库；
- storage；
- 配置文件；
- 日志。

正式部署可选择：

- 本地专用服务器；
- 云端服务器。

正式部署建议包括：

- FastAPI；
- PostgreSQL；
- Storage Service；
- Worker；
- Nginx；
- HTTPS；
- systemd / supervisor；
- 日志；
- 定期备份；
- 权限控制。

## 十五、OneClaw / OpenClaw 执行关系

执行链路为：

窗口1生成任务卡 → 窗口2生成代码包和代码包流转报告 → 窗口3检查代码包并生成执行器任务卡或命令卡 → OneClaw / OpenClaw 受控落位执行 → 窗口3处理执行器回传 → 窗口1接收任务级反馈并提出状态更新建议 → 窗口4在阶段完成后进行独立验收。

当前只允许三个技能：

- luopan-executor；
- luopan-preview；
- luopan-local-ops。

OneClaw / OpenClaw 不得：

- 自由写代码；
- 自由修 bug；
- 自由新增能力；
- 自由改字段；
- 自由改状态；
- 自由改权限；
- 自由改接口；
- 自由改页面；
- 自由改 .env；
- 自由改 API Key；
- 自由改正式数据库；
- 自由 commit / push。

## 十七、后续启用条件

| 能力 | 启用条件 |
|---|---|
| Capacitor App | H5 最小闭环稳定、后端 API 稳定 |
| PostgreSQL | 进入正式服务器部署、多用户使用或长期正式数据沉淀 |
| Alembic | 数据模型稳定，进入迁移管理 |
| Redis | 查询、会话、任务或缓存压力出现 |
| Celery | 异步任务明显增多，数据库任务表不足 |
| 对象存储 | 文件量增加、云端部署或多端访问需求增强 |
| SSE | AI / 文件 / 长任务进度需要实时反馈 |
| Nginx + HTTPS | 进入服务器测试部署或正式部署 |
| systemd / supervisor | 进入长期运行 |
| 云端 / 专用服务器 | 本地验证稳定、需要多设备 / App / 外部协同访问 |

- 原生 Android / iOS 双套代码；
- Flutter 重写；

- Elasticsearch；
- 向量数据库；
- 复杂 BI 平台；

这些不是永远不能做，而是不进入当前技术选型主线。

## 十九、四窗口使用规则

拆解与实现工作台在生成任务卡、代码包、执行器任务卡、执行器命令卡、回传处理报告或阶段验收报告时，必须遵守本文。

四窗口共同不得：

1. 临时更换技术栈；
2. 为单个任务引入未裁决的新框架；
3. 把 H5 写成最终形态；
4. 把 SQLite 写成唯一长期数据库；
5. 把本地文件绝对路径写入业务逻辑；
6. 让前端或 App 裁决正式事实；
7. 让 OneClaw / OpenClaw 自由写代码；
8. 跳过窗口2代码包生成直接让执行器开发；
9. 让窗口1代替窗口3生成执行器命令卡；
10. 让窗口3代替窗口2写代码或修 bug；
11. 让窗口4代替窗口2或窗口3修补执行问题。

如任务需要超出本文选型范围，必须先经用户裁决，并更新技术选型方案后再进入任务拆解或代码生成。

## 二十、最终裁决

罗盘系统采用全阶段可演进的轻量单体架构。

最终技术选型为：

- 前端：React + TypeScript + Vite；
- 移动端：Capacitor + Android / iOS App；
- PC 端：React Web；
- 后端：Python + FastAPI；
- 数据访问：SQLAlchemy + Repository + Service；
- 数据库：SQLite 阶段验证，PostgreSQL 正式运行目标；
- 迁移：Alembic 后续启用；
- 文件：Storage Service，本地先行，后续兼容对象存储；
- 任务：Task Service，数据库任务表 + Worker 先行，后续 Redis / Celery；
- AI：云端大模型 API + AI Service；
- 缓存：Cache Service 预留，Redis 后续启用；
- 权限：Access Control Service；
- 追溯：Audit / Trace Service；
- 接口：REST API + OpenAPI，SSE 后续预留；
- 部署：本地开发与本地部署验证先行，后续可迁移专用服务器或云端服务器；
