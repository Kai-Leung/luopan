# 13_履历记录细则

## 一、文件定位

本文是 `40_业务数据体系/02_事实记录层` 下的履历记录细则文件，用于定义员工、工人、班组、供应商、外协人员、设计师、项目负责人、客户、甲方代表、外部协作者等主体在项目参与、角色承担、协作经历、服务经历、执行表现、资料贡献、确认参与、异常经历、复盘反馈和关系演进中的履历类过程事实边界、入链条件、对象锚点、来源证据、确认要求、追溯要求，以及与主体资产、项目资产、其他事实记录、汇总视图层和经验规则层的关系。

履历记录用于回答“某个主体在什么项目、什么阶段、以什么角色参与过什么事项，形成了哪些可追溯经历、能力依据、协作依据、服务依据、风险依据或复盘依据”。

本文只定义主体履历过程事实的业务边界和开发依据，不替代主体资产、项目资产、组织资产、出勤记录、施工记录、财务记录、沟通与服务记录、问题与风险记录、责任与确认记录、商务维护记录、人事档案系统、绩效系统、供应商管理系统、客户关系管理系统、接口 schema、页面组件、数据库表结构或代码实现。本文不写字段全集、枚举全集、状态机、权限矩阵、测试脚本或实施计划。

## 二、履历记录职责

履历记录的核心职责，是把主体在项目、组织、协作和服务中的参与经历沉淀为可追溯事实，使系统能够基于真实事实理解主体曾经参与过什么、承担过什么、表现出什么可追溯特征、后续如何用于查询、筛选、协作、复盘和经营判断。

履历记录承担以下职责：

1. 定义履历类事实的成立条件；
2. 定义项目参与履历、角色履历、协作履历、服务履历、执行经历、资料贡献、确认参与、问题风险经历、复盘反馈和关系演进的边界；
3. 定义履历记录必须绑定主体、项目、事实来源、时间范围、角色或业务事项的规则；
4. 定义履历记录与主体资产之间的分层关系；
5. 定义履历记录与出勤、施工、资料、财务、沟通服务、问题风险、责任确认、商务维护等事实记录的边界；
6. 定义履历记录如何支撑主体查询、项目复盘、经营视图、执行视图、交付与协同视图和经验沉淀；
7. 定义候选履历事实与正式履历事实的边界；
8. 定义履历记录不得被页面标签、AI 评价、视图摘要、模板输出、主观印象或历史旧称反向定义。

履历记录不定义主体本体，不自动形成能力等级，不自动形成绩效结论，不自动形成奖惩结论，不自动形成黑名单，不自动形成供应商等级，不自动形成客户价值判断，不替代人事、绩效、法务、财务或完整 CRM / SRM 系统。

## 三、上位约束

履历记录必须服从以下上位约束：

1. 事实记录层只承接真实发生或经确认的过程，不承接稳定对象本体；
2. 履历记录是事实记录层中的事实类型之一，不得扩写成完整人事档案、绩效系统、供应商评级系统或客户关系系统；
3. 履历主体应绑定主体资产或候选主体，不得以姓名、昵称、电话、微信名、班组备注、供应商简称、客户称呼或页面标签直接替代主体锚点；
4. 项目相关履历应绑定项目资产；组织级履历应绑定组织资产或业务场景；
5. 履历记录应绑定来源事实、时间范围、角色或参与事项、权限判断和审计追溯；
6. 涉及能力评价、奖惩、黑名单、责任判断、客户评价、供应商评价、合同争议、付款争议和对外展示的履历内容，应按高风险事实或高风险候选处理；
7. 汇总视图层可以消费履历记录，但不得反写履历事实；
8. 经验规则层可以从履历记录中沉淀用人经验、班组协作经验、供应商协同经验、客户服务经验和规则候选，但不得覆盖履历事实；
9. AI 可以辅助整理候选履历、候选经历、候选标签和待补提示，但不得自动确认正式履历、正式评价、正式等级、正式奖惩或正式风险结论；
10. 页面标签、视图摘要、AI 评价、模板输出、导出包、分享包、前端 Mock 状态和历史资料，不得直接成为正式履历事实；
11. 历史旧称、旧分类体系、数据库表名、接口字段名、页面入口和代码模型名不得反向定义履历记录。

## 四、履历事实成立条件

一条内容能够进入履历记录，应同时满足以下条件：

1. 有明确主体资产、候选主体、班组主体、组织主体、客户主体、供应商主体或外部协同主体；
2. 有明确项目资产、组织资产、业务场景、服务场景、协作场景或候选归属锚点；
3. 有明确履历事项，例如项目参与、角色承担、任务协作、服务经历、资料贡献、确认参与、问题经历、风险经历、责任相关经历、复盘反馈或关系演进；
4. 有开始时间、结束时间、发生时间、确认时间、记录时间、时间范围或明确未知时间标记；
5. 有来源或证据；
6. 能说明履历类型、参与角色、参与事项、来源事实、影响范围、业务结果、待补内容或关联对象中的至少一种；
7. 有状态口径；
8. 有权限判断；
9. 涉及评价、等级、奖惩、责任、黑名单、供应商评价、客户价值、对外展示或高风险争议时，具备必要确认或待确认标记；
10. 具备审计追溯依据；
11. 不与已入链履历事实产生未处理冲突。

来源或证据存在，但其中的主体身份、项目归属、角色、时间范围、来源事实、业务事项或评价依据不清的，不视为无来源，应视为主体待识别、项目待补、角色待补、时间待补、来源待补或依据待补，进入待补、校验、挂起、驳回或人工确认流程，不得直接正式入链。

“待补、校验、挂起、驳回或人工确认流程”是事实记录层通用治理动作集合。各动作的触发条件、状态流转、权限要求、字段要求、提示规则和人工处理路径，由标准治理中的状态口径、校验规则、权限与可见性口径、追溯与版本口径，以及后续事实记录层通用治理流程承接。本文只在履历场景中指出应进入治理流程的业务情形，不定义完整状态机。

以下内容不得直接作为正式履历记录：

1. 只有姓名、项目名或一句“这个人干过”的无锚点描述；
2. 未识别主体、项目、角色、时间或来源的聊天截图、照片、日报、简历文本、供应商介绍、客户备注、语音转文字或图片摘要；
3. AI 从出勤记录、施工记录、沟通记录、资料记录、问题记录或财务记录中推测出的能力、表现、等级或风险结论；
4. 页面标签、前端草稿、接口载荷、模板输出、经营视图、客户画像、供应商画像或导出包中的主体描述；
5. 未能区分是主体资产、项目参与、出勤事实、施工事实、沟通服务、责任确认、问题风险、商务维护还是履历沉淀的混合描述；
6. 无权限来源提交的主体评价、客户评价、供应商评价或黑名单建议；
7. 缺少必要主体锚点、来源事实、时间范围或证据链的高风险履历内容。

上述内容应先作为候选履历事实、候选主体、待补项、待确认项、原始输入或运行中间数据处理。只有完成必要锚定、补齐、校验、权限判断和追溯后，才能进入正式履历记录。

## 五、履历记录承接范围

履历记录承接以下事实范围：

| 履历类型 | 承接内容 | 不承接内容 | 主要作用 |
|---|---|---|---|
| 项目参与履历 | 主体参与某项目、阶段、任务、工序、服务或协同事项的经历 | 项目本体、施工过程全集 | 主体经历追溯、项目复盘、后续协作参考 |
| 角色履历 | 主体在项目或组织中承担负责人、施工人、设计师、资料负责人、供应商、班组、客户代表等角色的事实 | 主体本体、权限系统全集 | 角色追溯、协作边界、责任线索 |
| 协作履历 | 主体与项目、客户、甲方、供应商、班组、员工或外部协作者的协作经历 | 关系资产本体、完整 CRM / SRM | 协作经验、风险提示、后续选择参考 |
| 服务履历 | 主体为客户、甲方、项目或组织提供服务、响应、协调、售后或问题处理的经历 | 服务承诺自动确认、客户价值结论 | 客户服务追溯、交付与协同视图 |
| 执行经历 | 主体参与施工、资料、财务、物资、确认、验收、风险处理等执行事项的经历摘要 | 具体事实本体 | 主体能力依据候选、项目复盘 |
| 资料贡献 | 主体提供、提交、补齐、确认或整理资料的经历 | 资料资产本体、资料记录全集 | 资料责任线索、结算准备、复盘依据 |
| 确认参与 | 主体参与客户确认、甲方确认、内部授权确认、责任确认或资料确认的经历 | 正式确认链路本体 | 责任追溯、协作追溯、风险判断 |
| 问题风险经历 | 主体关联问题、风险、整改、争议、异常或闭环处理的经历 | 责任终局裁决、风险管理系统 | 风险提示、复盘分析、治理回流 |
| 复盘反馈 | 主体相关项目复盘、服务反馈、协作反馈、问题反馈或经验线索 | 经验规则正式化 | 经验沉淀候选、后续优化 |
| 关系演进 | 主体从候选合作、首次协作、多次协作、复购、转介绍、终止合作等过程中的履历线索 | 主体关系资产本体、商务维护过程全集 | 合作历史、经营视图、商务维护参考 |
| 履历修正 | 对已记录履历的补充、修订、作废、归档、来源修正或版本回滚 | 静默覆盖旧记录 | 事实纠错、版本保护、审计追溯 |

履历记录承接主体经历的过程事实，不承接主体对象本体、项目对象本体、具体施工过程本体、财务收付款事实、责任终局裁决、完整评价体系、完整客户关系体系或完整供应商管理体系。

## 六、履历记录不承接范围

以下内容不得写入履历记录本体：

| 内容 | 正确归口 | 原因 |
|---|---|---|
| 员工、工人、班组、客户、甲方、供应商、外协人员等主体本体 | 主体资产 | 属于稳定主体对象 |
| 项目本体、项目范围、项目阶段、项目状态投影 | 项目资产 | 属于稳定项目对象 |
| 组织、公司、部门、资源池等组织对象 | 组织资产 | 属于稳定组织对象 |
| 到场、离场、工时、工天、缺勤、迟到、早退、加班 | 出勤记录 | 属于出勤过程事实 |
| 施工动作、现场进展、施工完成状态、返工施工 | 施工记录 | 属于施工过程事实 |
| 收付款、报销、开票、结算确认、工资付款 | 财务记录 | 属于财务事实 |
| 客户沟通、甲方沟通、服务响应、投诉沟通 | 沟通与服务记录 | 属于沟通服务事实 |
| 问题成立、风险识别、整改过程、风险关闭 | 问题与风险记录 | 属于问题风险事实 |
| 正式责任确认、授权确认、客户确认、甲方确认 | 责任与确认记录 | 属于确认链路事实 |
| 商机跟进、复购、转介绍、客户维护、供应商维护 | 商务维护记录 | 属于商务维护事实 |
| 履历看板、主体画像、供应商画像、客户画像、经验标签 | 汇总视图层、模板输出或经验规则层 | 属于输出、归纳或候选经验 |
| 完整人事档案、绩效评价、奖惩系统、供应商评级系统、客户价值体系 | 后续运行规则、外部系统或专门规则 | 超出本文职责 |
| AI 评价、页面标签、接口载荷、模板输出、导出包、分享包 | 候选内容或运行中间数据 | 不能直接成为正式履历事实 |

履历记录不得因为某项内容“涉及某个主体”“出现在视图里”或“可用于后续评价”而直接吸收该内容本身。被履历记录提及的主体、项目、出勤、施工、财务、沟通、问题、责任和商务维护，应按对应层级和事实类型归口。

## 七、主体资产与履历记录边界

主体资产回答“这个主体是谁”，履历记录回答“这个主体在项目、组织、协作、服务或经营过程中留下了什么可追溯经历”。

二者边界如下：

| 对比项 | 主体资产 | 履历记录 |
|---|---|---|
| 所属层级 | 对象资产层 | 事实记录层 |
| 主问题 | 主体是谁 | 主体经历了什么 |
| 核心内容 | 名称、类型、身份、联系方式、关系、归属、状态投影 | 项目参与、角色承担、协作经历、服务经历、执行经历、复盘反馈 |
| 是否记录单次过程 | 否 | 是 |
| 是否承接主体本体 | 是 | 否 |
| 是否承接经历事实 | 否 | 是 |
| 是否可作为视图消费来源 | 是 | 是 |
| 是否自动形成评价等级 | 否 | 否 |
| 是否自动形成奖惩或黑名单 | 否 | 否 |

履历记录与主体资产应遵守以下规则：

1. 主体资产承接主体本体；
2. 履历记录承接主体经历过程事实；
3. 主体资产不得吸收项目参与、出勤、施工、服务、问题、确认和商务维护等过程事实；
4. 履历记录不得定义主体正式名称、主体类型、联系方式、长期归属、主体关系和对象状态；
5. 履历记录可以触发主体候选创建、主体合并候选、主体身份修订候选或主体关系待确认，但不得静默覆盖主体资产；
6. 主体资产发生合并、作废、归档或版本变更后，已入链履历记录应保留原主体引用，不得自动替换；
7. 如需修订履历记录与主体资产之间的引用关系，应进入治理流程，并保留原引用、修订原因、操作者、时间、版本和追溯依据。

## 八、项目参与履历边界

项目参与履历必须绑定项目资产或候选项目，并说明主体参与的角色、阶段、事项、时间范围和来源依据。

项目参与履历应遵守以下规则：

1. 主体参与项目施工、管理、设计、资料、沟通、服务、供应、验收、结算、风险处理或售后协同，可以形成项目参与履历；
2. 项目参与履历不等于项目资产本体；
3. 项目参与履历不等于施工事实本体；
4. 项目参与履历不等于出勤事实全集；
5. 项目参与履历不等于能力评价或绩效结论；
6. 项目参与履历应尽可能绑定来源事实，例如出勤记录、施工记录、资料记录、沟通与服务记录、责任与确认记录、问题与风险记录或商务维护记录；
7. 项目归属不清时，应进入待补、校验、挂起、驳回或人工确认流程；
8. 同一主体跨多个项目形成履历时，应分别归属，不得混写为无项目边界的总括经历。

项目归档后新增履历记录，应区分历史补证、归档修订、售后服务、质保整改、复盘补充或新项目线索，不得静默覆盖原项目履历。

## 九、角色履历与协作履历边界

角色履历用于记录主体在某个项目、组织或协作场景中承担过的业务角色。协作履历用于记录主体与其他主体在项目执行、服务、供应、确认、问题处理或商务维护中的协作经历。

角色履历应遵守以下规则：

1. 角色履历应绑定主体、项目或组织、角色名称、时间范围和来源依据；
2. 角色履历不等于权限配置；
3. 角色履历不等于责任确认；
4. 角色履历不等于绩效评价；
5. 同一主体可以在不同项目或不同阶段承担不同角色；
6. 角色发生变化时，应形成履历修订或新履历记录，不得无痕覆盖旧角色；
7. 角色来自页面选择、AI 推测、聊天称呼或资料备注时，应作为候选角色，不得直接正式入链。

协作履历应遵守以下规则：

1. 协作履历应说明协作主体、协作对象、协作事项、协作时间、协作结果或来源依据；
2. 协作履历不等于主体关系资产本体；
3. 协作履历不等于商务维护记录；
4. 协作履历不等于正式责任确认；
5. 协作中出现争议、投诉、风险、扣款、赔付或责任问题时，应转入问题与风险记录或责任与确认记录；
6. 协作履历可以作为后续选择合作方、复盘服务质量或识别风险的事实依据之一，但不得自动形成等级或黑名单。

## 十、服务履历与商务维护边界

服务履历记录主体围绕客户、甲方、项目、售后、资料、问题处理或协同支持提供服务的经历。商务维护记录承接客户、甲方、供应商、合作方等主体的维护、跟进、复购、转介绍和经营关系推进过程。

二者边界如下：

1. 服务履历侧重主体曾经提供过什么服务或参与过什么服务场景；
2. 商务维护记录侧重商务关系推进、客户维护、复购线索、转介绍和合作机会管理；
3. 服务履历可以消费沟通与服务记录、问题与风险记录、验收与交付记录和商务维护记录中的事实线索；
4. 服务履历不得替代商务维护记录记录客户跟进过程；
5. 商务维护记录不得反向修改已入链服务履历；
6. 客户满意、客户价值、复购概率、合作等级等归纳性内容应作为候选视图或经验规则候选，不得由履历记录自动确认。

涉及客户评价、甲方评价、供应商评价和服务等级时，应保留评价主体、评价时间、评价范围、来源证据和权限边界，不得由 AI 摘要、页面标签或单次事件自动生成正式评价。

## 十一、执行经历、资料贡献与确认参与

执行经历、资料贡献和确认参与必须区分。

执行经历应遵守以下规则：

1. 执行经历可以来自施工记录、出勤记录、物资流转记录、资料记录、财务记录、决策与变更记录、责任与确认记录等事实记录；
2. 执行经历应说明主体参与事项、项目或组织归属、时间范围和来源事实；
3. 执行经历不等于具体施工事实本体；
4. 执行经历不等于能力等级；
5. 执行经历不得由单条视图摘要或 AI 归纳自动确认。

资料贡献应遵守以下规则：

1. 主体提供、提交、补齐、整理、确认、退回或归档资料的经历，可以形成资料贡献履历；
2. 资料贡献不等于资料资产本体；
3. 资料贡献不等于资料记录全集；
4. 资料贡献不等于资料质量评价；
5. 资料贡献涉及结算、验收、责任或争议时，应绑定来源事实和必要确认。

确认参与应遵守以下规则：

1. 主体参与客户确认、甲方确认、内部授权确认、责任确认、资料确认或验收确认的经历，可以形成确认参与履历；
2. 确认参与履历不替代责任与确认记录；
3. 确认参与履历不自动形成责任成立；
4. 确认参与履历不得静默修改确认链路；
5. 高风险确认参与应保留确认主体、确认范围、确认时间、来源证据和权限依据。

## 十二、问题风险经历与责任边界

履历记录可以承接主体与问题、风险、异常、整改、争议、投诉或责任线索相关的经历，但不得替代问题与风险记录或责任与确认记录。

问题风险经历应遵守以下规则：

1. 主体关联问题、风险、异常、投诉、整改、争议或关闭过程，可以形成问题风险经历；
2. 问题风险经历不等于问题成立；
3. 问题风险经历不等于责任确认；
4. 问题风险经历不等于处罚、扣款、赔付或黑名单；
5. 问题风险经历应绑定来源问题、风险或责任确认事实；
6. 问题风险经历被用于对外展示、供应商筛选、客户关系判断或内部奖惩时，应按高风险内容处理。

责任边界应遵守以下规则：

1. 履历记录可以保留责任线索、责任相关经历和确认参与经历；
2. 正式责任确认、授权确认、客户确认和甲方确认应归责任与确认记录；
3. 责任线索不等于责任成立；
4. 单次负面经历不等于主体等级下降、黑名单或合作终止；
5. AI、页面标签、风险看板或经营视图不得自动裁决主体责任或履历结论。

## 十三、履历时间与版本边界

履历记录必须区分经历发生时间、开始时间、结束时间、确认时间、系统记录时间和修订时间。

| 时间类型 | 含义 | 边界 |
|---|---|---|
| 发生时间 | 某项履历事项实际发生的时间 | 不等于系统记录时间 |
| 开始时间 | 某段参与、协作、服务或角色履历开始的时间 | 不代表已结束 |
| 结束时间 | 某段参与、协作、服务或角色履历结束的时间 | 不代表评价结论 |
| 确认时间 | 履历事项被人工确认或来源事实确认的时间 | 不替代发生时间 |
| 系统记录时间 | 用户、页面、接口或系统记录候选履历的时间 | 不代表履历事实发生时间 |
| 修订时间 | 对履历记录进行补充、修订、作废或引用修订的时间 | 不得覆盖原事实时间 |

履历时间不清时，应明确未知、待补或待确认，不得用默认当前时间冒充事实发生时间。来源事实时间、项目时间、出勤时间、资料时间、确认时间、系统时间或多个来源时间不一致时，应进入待补、校验、挂起、驳回、人工确认或事实修订流程。

履历记录变更不得无痕覆盖。补充、修订、作废、归档、引用修订、来源修正和版本回滚，应保留原记录、变更原因、操作者、时间、版本、影响范围和追溯依据。

## 十四、证据、来源与确认要求

履历记录应绑定来源或证据。来源可以来自主体资产、项目资产、出勤记录、施工记录、资料记录、沟通与服务记录、问题与风险记录、责任与确认记录、验收与交付记录、决策与变更记录、商务维护记录、复盘与反馈记录、人工录入、外部反馈、页面录入、接口载荷或其他可追溯来源。

证据与来源应遵守以下规则：

1. 来源存在不等于履历成立；
2. 主体名称存在不等于主体已确认；
3. 项目名称存在不等于项目归属已确认；
4. 出勤存在不等于项目参与履历完整；
5. 施工记录存在不等于能力评价成立；
6. 沟通记录存在不等于服务履历已确认；
7. 问题记录存在不等于责任履历成立；
8. AI 摘要不等于履历结论；
9. 页面标签不等于正式履历事实；
10. 视图摘要不等于履历事实本体；
11. 证据链断裂时，不得直接生成正式履历结论；
12. 证据冲突时，应进入待补、校验、挂起、驳回或人工确认流程。

影响主体评价、合作等级、奖惩、黑名单、责任、客户价值、供应商选择或对外展示的履历记录，应具备必要人工确认或明确待确认标记。

## 十五、候选履历事实与正式履历事实

履历记录必须区分候选履历事实和正式履历事实。

候选履历事实来源包括：

1. 用户手动录入；
2. 主体资产线索；
3. 项目记录；
4. 出勤记录；
5. 施工记录；
6. 资料记录；
7. 财务记录；
8. 沟通与服务记录；
9. 问题与风险记录；
10. 责任与确认记录；
11. 商务维护记录；
12. 验收与交付记录；
13. 复盘与反馈记录；
14. 日报周报；
15. 视图摘要；
16. 页面标签；
17. 外部反馈；
18. 接口载荷；
19. AI 辅助摘要；
20. 导入记录。

候选履历事实不得直接作为正式履历事实消费。候选履历事实进入正式履历记录前，应完成以下处理：

1. 判断履历事实类型；
2. 识别并确认主体、项目、组织或业务场景锚点，确保项目或组织归属已锚定；
3. 识别角色、参与事项、服务事项、协作事项、问题风险事项或确认参与事项；
4. 绑定来源事实或证据；
5. 识别开始时间、结束时间、发生时间、确认时间或时间范围；
6. 判断是否涉及评价、等级、奖惩、黑名单、责任、争议、客户价值、供应商选择或对外展示；
7. 判断权限与可见性；
8. 执行必要校验；
9. 标记待补、挂起、驳回、待确认或正式状态；
10. 保留审计追溯依据。

若候选履历事实中包含施工过程、出勤过程、财务收付款、商务维护、问题风险、责任确认、评价结论或客户承诺，应拆分或转归口到对应事实类型，不得以履历记录直接放行。

## 十六、履历记录生命周期边界

履历记录生命周期应至少支持以下治理动作：

1. 创建候选履历事实；
2. 补齐；
3. 校验；
4. 挂起；
5. 驳回；
6. 人工确认；
7. 正式入链；
8. 项目参与记录；
9. 角色记录；
10. 协作记录；
11. 服务记录；
12. 执行经历记录；
13. 资料贡献记录；
14. 确认参与记录；
15. 问题风险经历记录；
16. 复盘反馈记录；
17. 关系演进记录；
18. 关联来源事实；
19. 补充；
20. 修订；
21. 作废；
22. 归档；
23. 引用修订；
24. 来源修正；
25. 版本回滚。

上述动作之间的流转关系、状态名称、前置条件、权限要求、字段要求和校验规则，由系统业务运行规则、标准治理中的状态口径、追溯与版本口径、权限与可见性口径或相关承接文件按职责承接。本文只定义履历记录需要支持的生命周期治理动作范围，不定义完整状态机。

## 十七、与汇总视图层的关系

汇总视图层可以消费履历记录，生成经营视图、执行视图、结算视图和交付与协同视图中的主体履历相关结果。

| 汇总视图 | 可消费内容 | 禁止项 |
|---|---|---|
| 经营视图 | 主体合作历史、供应商协作经历、客户服务经历、风险经历、复盘线索 | 不自动形成主体等级、客户价值或供应商评级 |
| 执行视图 | 项目参与经历、角色经历、班组经历、人员安排依据、异常经历 | 不把视图摘要写成正式履历事实 |
| 结算视图 | 与人工成本、供应商、班组、资料贡献、确认参与相关的履历线索 | 不自动形成结算确认、付款事实或工资结论 |
| 交付与协同视图 | 对外可见的服务经历、参与角色、协作记录和确认参与摘要 | 不暴露内部评价、责任判断或未确认高风险经历 |

汇总视图层只能消费正式履历事实和授权范围内的候选内容。视图发现主体不清、项目不清、来源不清、时间冲突、评价依据不足、权限不足或高风险事项未确认时，只能生成待补项、候选问题或治理回流，不得反写履历记录。

主体画像、供应商画像、客户画像、履历看板、合作清单、经验标签和对外展示包属于视图输出、模板输出或业务输出，不是履历记录本体。

## 十八、与经验规则层的关系

经验规则层可以从履历记录中沉淀用人经验、班组协作经验、供应商协同经验、客户服务经验、风险识别经验、角色安排经验和模板优化候选。

履历记录与经验规则层的关系如下：

1. 多条履历事实可以形成主体协作经验和角色安排经验；
2. 高频问题、风险、争议、优质服务和稳定协作可以形成候选规则或提示；
3. 主体履历可以支撑后续项目安排、供应商选择、客户服务和项目复盘的候选建议；
4. AI 可以辅助归纳履历模式，但输出默认是候选经验；
5. 经验规则层不得直接修改履历记录；
6. 单条履历事实不得直接晋升为正式规则；
7. 经验规则层发现履历缺口时，只能生成待补项、候选问题或治理回流。

经验规则层服务后续优化，不替代履历记录本体，也不替代正式事实入链。

## 十九、与接口、页面、AI 和模板的关系

履历记录对接口、页面、AI 和模板形成以下约束：

1. 输入接口只能提交原始履历输入、候选履历事实、待补项、确认请求或受控写入，不得绕过校验直接创建正式履历事实；
2. 查询接口只能读取权限范围内的履历记录、候选履历事实或主体履历维度视图；
3. 页面可以展示候选履历、正式履历、来源事实、待补事项、阻断原因、确认入口和状态提示，但不得裁决正式评价、正式等级、奖惩、黑名单或高风险责任事项；
4. 页面补全项应以后端返回的缺失项、阻断原因、候选项和可选动作范围为准；
5. AI 可以辅助整理项目、出勤、施工、资料、沟通、问题风险、确认、商务维护和复盘记录中的履历内容，生成候选摘要、候选经历、候选标签和待补提示，但不得自动确认正式履历事实；
6. 模板可以读取履历记录生成主体履历摘要、项目复盘摘要、供应商协作摘要、客户服务摘要或经营视图草稿，但模板输出不得创建或修改正式履历事实；
7. 导出包、分享包、主体画像、供应商画像、客户画像和对外展示内容中的履历描述，不得反向修改履历记录；
8. 涉评价、等级、奖惩、黑名单、责任、客户价值、供应商选择和对外发布的履历相关内容，必须接受高风险校验和必要人工确认。

## 二十、禁止混写与反向定义规则

履历记录必须防止以下混写和反向定义：

1. 把履历记录写成主体资产、项目资产或组织资产；
2. 把出勤记录直接写成项目参与履历完整结论；
3. 把施工记录直接写成能力评价；
4. 把服务经历写成客户价值判断；
5. 把问题风险经历写成责任确认；
6. 把单次负面经历写成黑名单、等级下降或合作终止；
7. 把视图摘要、页面标签、主体画像、供应商画像、客户画像、日报周报、AI 摘要、接口回执或模板输出直接写成正式履历事实；
8. 让汇总视图层、经验规则层、页面、接口、模板或 AI 输出反向修改履历记录；
9. 静默修订履历记录、静默替换主体锚点、静默替换项目锚点、静默替换来源事实或无证据更新履历状态；
10. 用数据库表、接口字段、页面入口、代码模型名或历史旧称反向定义履历记录；
11. 把分步实施、页面便利、接口便利、技术预留或架构预留能力作为绕过履历治理、权限隔离、人工确认和追溯要求的理由；
12. 把履历记录写成自动画像系统、自动评级系统、自动绩效系统、自动黑名单系统、自动供应商筛选系统或自动客户价值判断能力；未来如需实现相关自动化能力，应由系统业务运行规则、标准治理、接口边界、权限与状态治理、测试验收等对应文件另行定义，并不得反向改变本文的履历事实边界、入链条件和追溯要求。

## 二十一、下游承接规则

## 二十二、边界判断

本文成立，应满足以下判断口径：

1. 能明确履历记录只承接项目参与、角色承担、协作经历、服务经历、执行经历、资料贡献、确认参与、问题风险经历、复盘反馈和关系演进等过程事实，不承接主体对象本体；
2. 能说明主体资产回答“主体是谁”，履历记录回答“主体经历了什么”；
3. 能说明履历记录与主体资产、项目资产、组织资产的锚定关系；
4. 能区分履历记录、出勤记录、施工记录、财务记录、沟通与服务记录、问题与风险记录、责任与确认记录和商务维护记录；

8. 能说明 AI 摘要、页面标签、接口回执、视图摘要、模板输出和导出包不得直接成为正式履历事实；
9. 能防止汇总视图层、经验规则层、页面、接口、模板或 AI 输出反向修改履历记录；
10. 能说明自动画像、自动评级、自动绩效、自动黑名单、自动供应商筛选或自动客户价值判断等能力即使未来实现，也必须由对应下游文件另行定义，且不得反向改变本文事实边界；
