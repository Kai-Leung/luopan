# 00_验证与验收规则总则

## 一、文件定位

本文定义罗盘系统验证与验收规则目录的总口径，用于约束后续验收标准、验证方案、验证场景集、回归验证规则、一致性检测规则、准出规则、前后端协同验收断言、高频错误与负向验证参考、能力边界验收断言总表的职责边界和承接关系。

本文只定义验证与验收目录负责什么、如何承接上游规则、如何设置验证边界、如何判断通过与失败、如何归口问题、如何形成准出判断，不定义系统规则来源、架构定义、业务运行流程、接口实现、页面实现、自动化测试代码、数据库结构、部署方案或实施计划。

验证与验收规则的核心作用，是验证罗盘系统是否按已定义的顶层定义、系统架构、标准治理、业务数据体系、系统业务运行规则、接口边界和页面承接边界运行。验收文件只能验证上游已经定义的能力和边界，不得通过测试结果反向新增能力、字段、枚举、状态、权限、事实类型、接口、页面或业务规则。

## 二、80 目录总职责

`80_验证与验收规则` 承担以下职责：

1. 定义罗盘系统开发依据的验收维度、验收标准、验证方案、验证场景、回归规则、一致性检测和准出判断口径。
2. 验证系统定位、架构层级、标准治理、业务数据体系、业务运行规则、接口边界和页面承接是否被正确继承。
3. 验证原始输入、候选内容、正式事实、汇总视图结果、经验规则候选、接口回执、页面状态、外部反馈和 AI 辅助输出是否保持边界。
4. 验证权限、状态、风险、校验、追溯、版本、脱敏、外部展示和失败回退是否按上游规则执行。
5. 验证页面、接口、AI、外部系统、Mock、回执、输出结果和汇总视图是否没有反向定义真源。
6. 验证开发、联调、测试和阶段准出时是否具备可判断、可追溯、可回归、可阻断的验收依据。
7. 将验证失败问题归口到对应上游目录或下游修订文件，防止在验收文件中直接修正规则。

80 目录不是业务规则目录，不是接口契约目录，不是页面设计目录，不是测试脚本目录，不是代码实现目录，也不是部署运维目录。

## 三、验证与验收总原则

验证与验收规则必须遵守以下原则：

1. 验证只验证已经定义的能力、规则和边界，不新增未被上游支撑的系统能力。
2. 验收只判断是否满足上游依据，不反向修改上游规则。
3. 测试通过不等于业务能力自动扩展，测试失败不等于业务事实不成立。
4. 功能可用不等于治理边界通过。
5. 页面展示正常不等于正式事实成立。
6. 接口返回成功不等于业务确认完成。
7. AI 输出可用不等于 AI 可裁决。
8. Mock 通过不等于真实接口通过。
9. 联调通过不等于阶段准出完成。
10. 外部系统返回成功不等于系统内部正式确认。
11. 汇总视图展示结果不等于新增事实。
12. 验收文件不得以测试便利性压低权限、状态、追溯、风险和真源边界。

验证与验收规则应同时覆盖正向能力是否能跑通、负向边界是否能拦截、一致性是否保持、回归后是否不破坏旧边界，以及阶段准出是否具备依据。

## 四、验证对象范围

验证与验收规则应覆盖以下对象：

| 验证对象 | 验证重点 | 不得误判为 |
|---|---|---|
| 顶层定义 | 系统定位、第一用户、第一业务验证场景、系统边界是否被继承 | 验收文件重新定义系统定位 |
| 系统架构 | L0-L7、横向治理、双回流、一池双区、组织隔离、运行主链路和读写边界是否被遵守 | 测试结果反向定义架构层级 |
| 标准治理 | 术语、字段、枚举、状态、权限、风险、校验、追溯、反问、脱敏、AI 辅助与候选输出口径是否被执行 | 验收文件新增标准 |
| 业务数据体系 | 对象资产层、事实记录层、汇总视图层、经验规则层的真源与衍生边界是否被保持 | 页面、接口或视图创造事实 |
| 系统业务运行规则 | L0-L7 运行、候选转正式、回流挂接、资料存储、授权输出和业务主链路是否按规则推进 | 验收直接裁决业务流转 |
| 接口边界与集成约束 | 输入、映射、回执、失败、页面动作、联调、X1 外部连接是否未越界 | 接口成功等于业务确认 |
| 前后端协同边界与页面承接 | 页面是否只展示处理方向和上游结果，未反写真源 | 页面动作直接完成入链 |
| AI 辅助输出 | AI 输出是否保持候选属性，是否未替代确认、裁决、入链和发布 | AI 结果成为正式事实 |
| 外部协同 | 外部反馈、外部回执、外部展示是否按脱敏、权限和回流边界承接 | 外部反馈直接改写正式事实 |
| 失败与熔断 | 失败、阻断、撤回、纠偏、熔断是否被记录并停止越界扩散 | 失败被隐藏为成功 |

## 五、验证类型

80 目录下游文件应按以下验证类型展开：

| 验证类型 | 主要作用 | 下游承接 |
|---|---|---|
| 验收标准 | 定义系统、目录、能力、边界是否通过的判断标准 | `01_验收标准.md` |
| 验证方案 | 定义验证组织方式、验证对象、验证顺序、验证结果归口 | `02_验证方案.md` |
| 验证场景 | 定义典型输入、候选、入链、查询、输出、外部协同和异常场景 | `03_验证场景集.md` |
| 回归验证 | 定义修改、归集、升版、修补后如何确认旧边界未被破坏 | `04_回归验证规则.md` |
| 一致性检测 | 定义跨目录、跨层级、跨接口、跨页面、跨状态和跨版本的一致性检查 | `05_一致性检测规则.md` |
| 准出规则 | 定义进入下一阶段、下一组文件、归集包或开发任务前的通过条件 | `06_准出规则.md` |
| 前后端协同验收断言 | 定义页面动作、接口返回、状态提示、Mock、联调和外部协同的验收断言 | `07_前后端协同验收断言.md` |
| 负向验证参考 | 定义高频错误、越权、反写真源、误展示、默认成功等负向验证参考 | `08_高频错误与负向验证参考.md` |
| 能力边界验收总表 | 汇总能力归口、承接关系、禁止项和验收断言 | `09_能力边界验收断言总表.md` |

验证类型可以组合使用，但不得相互替代。正向功能跑通后，仍必须通过负向边界、一致性、回归和准出检查。

## 六、验证断言基本模型

验证与验收应采用断言化表达。每条验收断言至少应回答：

| 断言要素 | 说明 |
|---|---|
| 验证对象 | 被验证的是输入、候选、事实、视图、接口、页面、回执、外部反馈、AI 输出还是失败处理 |
| 上游依据 | 断言来源于哪个上游目录或文件 |
| 应满足条件 | 正常情况下必须满足什么边界 |
| 不得出现结果 | 哪些结果一旦出现即判定失败 |
| 失败归口 | 失败后应回到哪个目录、文件或规则处理 |
| 准出影响 | 失败是否影响当前文件、当前目录、当前阶段或当前包准出 |

断言不得写成“功能正常”“页面可用”“接口成功”“展示正确”等模糊表达。验收判断必须能明确区分通过、失败、阻断、待补、挂起、回归失败和准出失败。

## 七、正向验证边界

正向验证用于确认系统能力是否按上游规则正常承接。正向验证应覆盖以下内容：

1. 原始输入是否能被接收、保留来源并进入输入链路。
2. 候选内容是否能生成、展示候选属性并进入后续处理。
3. 必要字段缺口是否能触发关键字段反问与补齐承接。
4. 正式事实是否只能由 L2 真源入链层产生。
5. 汇总视图层是否能基于对象资产层和事实记录层消费结果。
6. 经验规则层是否只能沉淀候选经验、模板候选和规则候选。
7. 接口是否能返回接收、待补、挂起、阻断、失败、回执、撤回、纠偏或熔断等处理方向。
8. 页面是否能展示接口处理方向和上游结果。
9. 查询是否能按权限范围返回结果或脱敏结果。
10. 外部协同是否能提交反馈、补充资料和确认线索，并保持候选或回执属性。

正向验证不得只验证功能是否可操作，还应验证操作结果是否保持正确归口和正确边界。

## 八、负向验证边界

负向验证用于确认系统能否拦截越界、污染、误展示和错误放行。负向验证应覆盖以下内容：

1. 原始输入来源不明时，不得直接进入正式事实链。
2. 候选内容未经治理和确认时，不得展示为正式事实。
3. 资料上传、识别、挂接成功时，不得展示为资料有效或证据成立。
4. 页面确认、弹窗确认、批量勾选时，不得等同于 L2 入链。
5. 回执成功、输出成功、外部系统 success 时，不得展示为业务确认完成。
6. AI 辅助预处理结果不得成为正式事实、正式状态、正式规则或自动放行结果。
7. 查询空结果不得展示为事实不存在。
8. 无权限结果不得展示为数据不存在。
9. 外部反馈不得直接改写责任、金额、验收、结算、状态或正式事实。
10. 失败、阻断、撤回、纠偏和熔断不得被页面隐藏为成功。

负向验证失败时，应优先判断是否存在页面误展示、接口越界、业务运行链路缺口、标准治理缺口或数据体系归口错误，不得在验收文件中直接补写新规则。

## 九、一致性检测边界

一致性检测用于确认不同目录、文件、接口、页面和状态表达是否同口径。

一致性检测至少覆盖：

| 检测对象 | 检测要求 |
|---|---|
| 目录职责一致性 | 10-80 目录职责不得互相替代或反向覆盖 |
| 术语一致性 | 正式术语、旧称禁用、层级名称、文件名称应保持一致 |
| 层级一致性 | L0-L7、对象资产层、事实记录层、汇总视图层、经验规则层不得混写 |
| 真源一致性 | 正式事实、状态真源、权限判断、证据链和追溯来源不得被页面或接口改写 |
| 接口页面一致性 | 60 返回的处理方向应被 70 正确展示 |
| 权限一致性 | 查询、导出、外部展示、追溯查看应受同一权限边界约束 |
| 状态提示一致性 | 页面状态不得新增正式状态口径 |
| 回执一致性 | 回执处理方向不得被展示为业务确认 |
| 版本一致性 | 文件版本、输出版本、资料版本、纠偏版本和回归记录应可追溯 |
| 准出一致性 | 验收通过、联调通过、回归通过和阶段准出不得互相替代 |

一致性检测发现冲突时，应先归口到对应上游目录或当前文件组，不得由一致性检测文件直接改写上游正文。

## 十、回归验证边界

回归验证用于确认文件修改、目录归集、版本升版、接口调整、页面承接调整、规则修补和正式包更新后，既有边界没有被破坏。

以下情况必须触发回归验证：

1. 修改已正式化文件。
2. 归集目录进入当前基准包。
3. 升级正式开发依据包版本。
4. 修改字段、状态、权限、校验、追溯、反问、脱敏或 AI 口径。
5. 修改 L0-L7 运行规则或候选转正式边界。
6. 修改接口边界、页面承接或外部协同边界。
7. 修复越权、误展示、回执误判、失败隐藏、Mock 混入正式结果等问题。
8. 发现 downstream 指向、YAML 表头、术语或路径存在冲突。
9. 执行归集前联检、全包联检或准出判断。
10. 进入下一阶段开发或下一组文件写作前。

回归验证不得只复测被修改点，还应检查其上游依赖、直接下游、同组总表和相关禁止项是否仍然成立。

## 十一、准出判断边界

准出判断用于确认当前文件、当前目录、当前基准包或当前阶段是否可以进入下一步。

准出判断至少区分以下层级：

| 准出层级 | 判断内容 |
|---|---|
| 单文件准出 | 当前文件职责、边界、术语、YAML、上下游和禁止项是否合格 |
| 目录准出 | 同目录文件是否齐全、职责是否闭合、总表是否收口、无职责冲突 |
| 归集准出 | 文件是否可写入当前基准包，是否需更新 tree / manifest，是否需升包版本 |
| 包级准出 | 全包目录、路径、上下游、术语、文件状态、版本和冲突检测是否通过 |
| 开发准出 | 当前开发依据是否足以支撑后续详细设计、开发、联调和验收 |
| 阶段准出 | 当前阶段是否满足已定义的验收标准、负向验证、一致性检测和回归要求 |

准出通过只表示可以进入下一步，不表示系统已经完成所有未来能力。预留能力不得因准出通过而被写成当前已完成能力。

## 十二、失败归口规则

验证失败时，应按问题性质归口处理：

| 失败类型 | 归口位置 |
|---|---|
| 系统定位、第一用户、第一场景、系统边界不一致 | `10_顶层定义` |
| 架构层级、L0-L7、读写边界、双回流、一池双区不一致 | `20_系统架构` |
| 字段、枚举、状态、权限、风险、校验、追溯、反问、脱敏、AI 口径不一致 | `30_标准治理` |
| 对象资产层、事实记录层、汇总视图层、经验规则层归口错误 | `40_业务数据体系` |
| 运行链路、候选转正式、回流、资料存储、授权输出规则错误 | `50_系统业务运行规则` |
| 输入、映射、回执、失败、页面动作、X1 外部连接越界 | `60_接口边界与集成约束` |
| 页面展示、页面状态、页面动作、查询结果、外部协同误承接 | `70_前后端协同边界与页面承接` |
| 验收断言不清、负向验证不足、回归规则缺失、准出判断不闭合 | `80_验证与验收规则` |
| 涉及代码、接口实现、页面实现、数据库、部署或测试脚本 | 后续详细设计或开发实现文件，不在 80 正文补写 |

失败归口不等于立即修改。是否修改、由哪个文件修改、是否需要升版、是否阻断，应按上游优先级和当前任务边界判断。

## 十三、与 60 和 70 的承接关系

80 目录应直接承接 60 和 70 已定义的接口与页面边界。

| 上游文件组 | 80 验证重点 | 不应作为通过依据 |
|---|---|---|
| 60_接口边界与集成约束 | 接口是否按输入、映射、回执、失败、页面动作、联调、X1 控制边界返回处理方向 | 接口返回 success |
| 70_前后端协同边界与页面承接 | 页面是否按处理方向展示，并未误写成正式事实、正式状态或正式确认 | 页面显示成功 |
| 60/08 接口边界承接总表 | 接口动作归口是否清楚、无冲突、无遗漏 | 表格存在但无法指导归口 |
| 70/09 页面动作与接口承接总表 | 页面动作与接口归口是否一致，是否可形成验收断言 | 页面动作可点击 |

80 目录不得重新定义 60 的接口边界，也不得重新定义 70 的页面承接。验收断言只能检查 60 和 70 是否被正确执行和正确展示。

## 十五、验证与验收禁止事项

80 目录及其下游文件禁止出现以下行为：

1. 禁止通过验收文件新增系统能力、字段、枚举、状态、权限、事实类型、接口能力、页面能力或业务边界。
2. 禁止通过测试结果反向改写顶层定义、系统架构、标准治理、业务数据体系、业务运行规则、接口边界或页面承接。
3. 禁止把功能可用、接口成功、页面显示、Mock 通过、联调通过直接写成阶段准出完成。
4. 禁止只测正向功能，不测负向边界、权限边界、真源边界、回执边界、页面误展示和失败回退。
5. 禁止把 AI 输出、外部反馈、接口回执、页面状态、汇总视图结果或测试样例写成正式事实。
6. 禁止验收文件定义接口 URL、HTTP 方法、JSON schema、数据库字段、页面布局、组件样式、测试脚本、部署命令或代码实现。
7. 禁止验收文件替代问题归口文件进行正文修订。
8. 禁止用“通过”“正常”“成功”“可用”等模糊词作为唯一验收判断。
9. 禁止忽略失败、阻断、挂起、撤回、纠偏、熔断和权限不足等负向结果。
10. 禁止把预留能力、后续阶段能力或 Mock 能力写成当前已完成能力。

## 十六、总体验收判断口径

本文成立后，应能支撑以下判断：

1. 能明确 `80_验证与验收规则` 目录的职责范围和禁止边界。
2. 能区分验收标准、验证方案、验证场景、回归验证、一致性检测、准出规则、前后端协同验收断言、负向验证参考和能力边界总表的分工。
3. 能确认验收文件只验证上游规则，不新增或反向改写上游规则。
4. 能确认验收必须覆盖功能可用、治理边界、数据真源、权限状态、接口页面、外部协同、AI 候选、失败回退和准出判断。
5. 能确认页面、接口、AI、外部系统、Mock、回执和汇总视图不会因验收通过而被升格为真源。
6. 能为后续详细设计、开发联调、测试执行和阶段准出提供可执行的验收依据。
