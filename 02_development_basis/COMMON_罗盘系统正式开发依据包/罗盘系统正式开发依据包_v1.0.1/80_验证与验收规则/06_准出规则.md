# 06_准出规则

## 一、文件定位

本文定义罗盘系统开发依据在单文件、目录、归集、包级、开发和阶段推进中的准出规则，用于判断当前成果是否可以进入正式化、归集、升版、下一目录写作、详细设计、开发拆解、联调验证或阶段关闭。

本文只定义准出层级、准出条件、必要检查、阻断条件、非阻断问题处理、准出结论输出和失败归口，不定义业务规则来源、接口协议、页面布局、测试脚本、自动化代码、数据库结构、部署方案或实施计划。

准出规则的核心作用，是把验收标准、验证方案、验证场景、回归验证和一致性检测结果转化为“能否进入下一步”的判断。准出通过只表示当前层级可以继续推进，不表示系统已经完成所有未来能力，也不表示预留能力已经实现。

## 二、准出总原则

准出判断应遵守以下原则：

1. 准出必须基于验收标准、验证方案、验证场景、回归验证和一致性检测结果，不得只凭主观判断。
2. 准出必须明确准出层级，不得把单文件通过放大为目录通过、包级通过或阶段通过。
3. 准出必须区分阻断问题和非阻断问题。
4. 准出不得通过降低真源、权限、状态、回执、失败、AI、外部协同和页面承接边界取得。
5. 准出不得以页面可显示、接口 success、Mock 通过、联调通过、文档已生成作为唯一依据。
6. 准出失败必须明确归口目录或文件，不得在准出规则中补写业务规则。
7. 涉及新增字段、枚举、状态、权限、事实类型、接口能力、页面能力或业务边界时，应阻断并请求裁决。
8. 准出通过后仍需保留可回归条件；后续修改、归集、升版或开发前应重新回归。

## 三、准出层级

准出分为六个层级：

| 准出层级 | 准出对象 | 主要判断 | 通过后允许进入 |
|---|---|---|---|
| S1 单文件准出 | 当前目标文件 | 当前文件是否可正式化 | 当前文件正式稿生成 |
| S2 目录准出 | 当前目录文件组 | 同目录是否齐全、闭合、总表收口 | 归集前联检或下一目录写作 |
| S3 归集准出 | 待归集文件组 | 文件是否可写入当前基准包 | 归集入包和包级升版 |
| S4 包级准出 | 新基准包 | 新包是否完整、版本是否唯一、tree/manifest 是否一致 | 作为后续写作基线 |
| S5 开发准出 | 当前开发依据包 | 是否足以支撑详细设计、任务拆解、接口页面和联调验收 | 开发拆解或详细设计 |
| S6 阶段准出 | 当前阶段成果 | 当前阶段正向、负向、一致性、回归和问题归口是否闭合 | 阶段关闭或进入下一阶段 |

任何准出层级都不得替代更高层级准出。S1 通过不代表 S2 通过；S4 通过不代表 S5 通过；S5 通过不代表 S6 通过。

## 四、S1 单文件准出规则

| 准出条件 | 通过标准 | 阻断标准 |
|---|---|---|
| 当前目标文件明确 | 文件职责与任务卡一致 | 当前目标文件不明确或任务卡缺失 |
| 文件状态正确 | 草稿、修改稿、正式稿状态符合阶段 | 状态错误或正式化前仍为草稿 |
| YAML 合规 | 表头字段、路径、标题、版本、上下游合规 | 表头越界、路径错位、title/H1 不一致 |
| 正文归口正确 | 只写当前文件职责 | 写入其他目录职责、上游规则或下游内容 |
| 术语一致 | 使用当前正式术语 | 旧称残留、混称或自创术语影响理解 |
| 禁止内容未出现 | 无代码、SQL、schema、页面布局、部署、技术选型 | 出现实现内容或测试脚本 |
| 未新增能力 | 未新增字段、状态、权限、事实类型、接口能力、页面能力 | 借正文新增能力或业务边界 |
| 自检通过 | 已完成 R1 单文件回归 | 未自检或自检发现阻断点未处理 |

S1 通过后，可以生成当前文件正式稿。S1 未通过时，不得生成正式稿。

## 五、S2 目录准出规则

| 准出条件 | 通过标准 | 阻断标准 |
|---|---|---|
| 文件齐全 | 任务卡规划文件全部完成 | 缺文件、编号断裂或总表缺失 |
| 总则成立 | 总则能约束全目录下游 | 总则与细则冲突或不能支撑下游 |
| 细则归口清楚 | 各细则职责单一，不互相覆盖 | 多篇文件重复定义或相互反写 |
| 总表收口 | 总表能汇总职责、动作、归口和下游承接 | 总表不能指导归口或新增规则 |
| 术语一致 | 同目录术语一致 | 同组混用旧称或不稳术语 |
| 上下游合理 | 同组 YAML 直接上下游合理 | 展开间接链路、虚构下游或错指上游 |
| 禁止项未突破 | 同组未写入禁止内容 | 某文件混入代码、schema、页面布局等 |
| R2 回归通过 | 已完成目录级回归 | 目录级回归存在阻断点 |

S2 通过后，可以进入归集前联检或下一目录写作。若当前目录是阶段最后一组，应进入 S3 归集准出。

## 六、S3 归集准出规则

| 准出条件 | 通过标准 | 阻断标准 |
|---|---|---|
| 文件状态 | 待归集文件均为正式稿 | 存在草稿或修改稿 |
| 路径一致 | 文件实际路径与 canonical_path 一致 | 文件路径错位或旧路径残留 |
| YAML 合规 | 表头字段、标题、版本、上下游合规 | 表头越界或路径错误 |
| 内容一致 | 待归集文件与已审定正式稿一致 | 文件内容被篡改或缺失 |
| 术语检查 | 无旧称残留和不稳术语 | 旧称残留影响正式口径 |
| 禁止内容检查 | 未写入代码、schema、页面布局、部署、技术选型 | 出现禁止内容 |
| 同路径覆盖可裁决 | 与当前基准包同路径文件可明确覆盖 | 多版本冲突无法裁决 |
| R3 回归通过 | 归集前回归无阻断点 | 归集前回归失败 |

S3 通过后，才可执行归集入包。归集前不得提前更新 tree / manifest；tree / manifest 应在归集入包时同步。

## 七、S4 包级准出规则

| 准出条件 | 通过标准 | 阻断标准 |
|---|---|---|
| 包版本 | 新包版本高于旧包且唯一 | 最高版本无法唯一确认 |
| 包结构 | 目录和文件落位正确 | 目录缺失、重复、错位 |
| 文件数量 | 文件数量符合归集结果 | 文件异常减少、重复或缺失 |
| tree/manifest | 已同步更新并与包内结构一致 | tree/manifest 缺失或不一致 |
| 压缩包完整性 | 压缩包可打开、可读取 | 压缩包损坏或关键文件缺失 |
| 旧包关系 | 旧包仅作为历史参考 | 旧包继续压制新包 |
| 新包可读 | 后续写作可读取新包必要文件 | 新包无法作为基线 |
| R4 回归通过 | 包级回归无阻断点 | 包级回归失败 |

S4 通过后，新包可以作为当前最高基准包继续写作。S4 未通过时，不得把新包作为当前基准使用。

## 八、S5 开发准出规则

| 准出条件 | 通过标准 | 阻断标准 |
|---|---|---|
| 当前基准包明确 | 当前最高开发依据包唯一 | 多版本基准包冲突 |
| 核心目录齐全 | 10-80 中当前开发所需目录已形成可承接依据 | 关键目录缺失，开发只能靠猜测 |
| 真源边界清楚 | 对象、事实、视图、经验规则和 L2 入链边界清楚 | 页面、接口、AI、外部反馈可能反写真源 |
| 接口页面边界清楚 | 60 与 70 可支撑接口和页面设计 | 接口或页面只能靠开发自行解释 |
| 验收断言可用 | 80 能支撑验证、回归、一致性和准出判断 | 缺少验收依据或负向边界 |
| 禁止项明确 | 代码实现不得越过 Raw Store、L0-L7、候选、确认、Audit/Trace 等边界 | 开发任务会自由补规则或改数据 |
| R5 回归通过 | 开发前回归无阻断点 | 开发前回归失败 |

S5 通过只表示可以进入详细设计、任务拆解或开发准备，不表示可以跳过具体开发任务审查、代码审查、联调和验收。

## 九、S6 阶段准出规则

| 准出条件 | 通过标准 | 阻断标准 |
|---|---|---|
| 阶段目标 | 当前阶段目标已被明确验证 | 阶段目标不清或与上游冲突 |
| 正向验证 | 核心正向场景通过 | 只验证孤立功能，无法支撑阶段闭环 |
| 负向验证 | 越权、反写、误展示、失败隐藏等负向边界通过 | 负向边界失败 |
| 一致性检测 | 跨目录、跨接口、跨页面一致性通过 | 存在无法裁决冲突 |
| 回归验证 | 修改、归集、升版后回归通过 | 回归失败或未回归 |
| 问题归口 | 阻断问题清零，非阻断问题有归口 | 阻断问题未处理 |
| 阶段成果 | 文档、归集包、验证结论、准出判断可追溯 | 阶段成果不可追溯 |
| 下一阶段承接 | 下一阶段有明确上游依据 | 下一阶段只能靠猜测推进 |

S6 通过后，才可关闭当前阶段或进入下一阶段。S6 不得由单个文件、单个目录、单次联调或单个功能通过替代。

## 十、阻断准出条件

出现以下情况时，应阻断对应准出：

1. 当前最高基准包无法唯一确认。
2. 当前目标文件任务卡缺失或目标文件职责不明。
3. 文件 YAML 越界、路径错位、title/H1 不一致。
4. 待归集文件不是正式稿。
5. 目录规划文件缺失或总表无法收口。
6. 新增字段、枚举、状态、权限、事实类型、接口能力、页面能力或业务边界。
7. 页面、接口、AI、外部反馈、回执、汇总视图反写正式事实。
8. 权限越界、脱敏失败、未授权展示或越权导出未被阻断。
9. 回执成功、输出成功、外部 success 被写成业务确认完成。
10. Mock、联调、演示结果被写成真实业务结果。
11. 失败、阻断、撤回、纠偏或熔断被隐藏为成功。
12. 代码、SQL、接口 schema、数据库结构、页面布局、部署脚本或技术选型进入正式开发依据正文。
13. 归集后 tree/manifest、文件数、包结构或压缩包完整性不通过。
14. 开发前核心边界不足，开发只能靠自行补规则。

## 十一、非阻断问题处理规则

以下问题通常不直接阻断，但应记录并在合适节点处理：

| 非阻断问题 | 处理方式 |
|---|---|
| 少量重复边界说明 | 归集前轻量收口 |
| 总则文件偏上位 | 可保留，不强制压成细则 |
| 个别术语不够精确但不影响边界 | 定向术语收口 |
| 同组文件版本不完全一致 | 归集时统一升包版本，不强制全部文件同版 |
| downstream 指向规划内但后续文件名可能调整 | 后续写作或归集时校准 |
| 单篇断言不够矩阵化 | 在总表或下游断言文件中收口 |
| 正文略长但无越界 | 不阻断 |
| 正文略短但职责覆盖完整 | 可继续，必要时在总表补强 |

非阻断问题不得用于掩盖阻断问题。若非阻断问题累计影响目录职责、术语一致、归口判断或准出判断，应升级为待补或阻断。

## 十二、准出结论输出口径

准出结论应按以下格式输出：

| 输出项 | 内容要求 |
|---|---|
| 当前结论 | 明确准出、待补、阻断、可归集、可升版、可继续写作、可进入开发或不可继续 |
| 准出层级 | 明确属于 S1、S2、S3、S4、S5 或 S6 |
| 检查范围 | 说明本次检查的文件、目录、包、阶段或开发依据范围 |
| 阻断点 | 只列影响当前准出的阻断问题 |
| 非阻断问题 | 列出不影响当前准出但需记录或后续处理的问题 |
| 可继续条件 | 说明下一步可正式化、归集、升版、继续写作、进入开发或需先修补 |
| 失败归口 | 对失败项说明归口目录或文件 |
| 版本影响 | 说明是否需要文件升版、包升版或无需升版 |
| 回归要求 | 说明是否已完成 R1-R5 回归或是否需补回归 |

准出结论不得只写“可以”“通过”“没问题”，必须明确准出层级和通过范围。

## 十三、准出失败处理规则

准出失败应按以下规则处理：

1. 失败归口当前文件时，应定向修补当前文件并执行 R1 回归。
2. 失败归口当前目录时，应修补对应文件或总表并执行 R2 回归。
3. 失败归口归集前检查时，应停止归集并执行 R3 回归。
4. 失败归口包级时，应停止使用新包并执行 R4 回归。
5. 失败归口开发准出时，应停止开发拆解或执行器任务，并执行 R5 回归。
6. 失败涉及新增字段、枚举、状态、权限、事实类型、接口能力、页面能力或业务边界时，应阻断并请求裁决。
7. 失败涉及上游正文依据冲突且无法裁决时，应阻断。
8. 修补完成后，应重新执行同层级准出判断。

准出失败不能用人工承诺、后续再改、页面临时提示、接口临时返回、Mock 通过或正向功能通过抵消。

## 十四、与下游文件的关系

| 下游文件 | 本文提供的支撑 | 下游不得做的事 |
|---|---|---|
| 07_前后端协同验收断言.md | 提供前后端协同验收进入准出的层级判断 | 不把联调通过直接写成阶段准出 |
| 09_能力边界验收断言总表.md | 提供能力边界断言是否影响准出的判断依据 | 不新增能力或扩大准出范围 |
| 80 其他验收文件 | 提供验证、回归、一致性结果如何转化为准出结论的规则 | 不用局部通过替代准出 |

## 十五、禁止事项

准出规则禁止出现以下行为：

1. 禁止把准出规则写成测试脚本、自动化代码、接口调用说明、页面操作流程或部署步骤。
2. 禁止通过准出规则新增字段、枚举、状态、权限、事实类型、接口能力、页面能力或业务边界。
3. 禁止把单文件通过、目录通过、归集通过、包级通过、开发准出和阶段准出互相替代。
4. 禁止把功能可用、页面显示、接口 success、Mock 通过、联调通过直接写成准出完成。
5. 禁止负向验证、回归验证、一致性检测未完成时直接准出。
6. 禁止为通过准出而降低真源、权限、状态、风险、追溯、脱敏、回执和失败边界。
7. 禁止把预留能力、后续阶段能力或演示能力写成当前已完成能力。
8. 禁止准出失败后强行正式化、归集、升版、继续写作或进入开发。
9. 禁止用“基本可以、问题不大、先过、后面补”替代准出判断。
10. 禁止准出文件反向修订 10-70 目录正文依据。

## 十六、准出规则成立条件

本文成立后，应能支持以下判断：

1. 能区分 S1 单文件准出、S2 目录准出、S3 归集准出、S4 包级准出、S5 开发准出和 S6 阶段准出。
2. 能明确每一层准出的通过标准、阻断标准和可继续条件。
3. 能判断阻断问题和非阻断问题。
4. 能说明准出失败后的处理方式和回归要求。
5. 能防止局部通过被放大为阶段通过。
6. 能支撑前后端协同验收断言和能力边界验收断言总表展开。
